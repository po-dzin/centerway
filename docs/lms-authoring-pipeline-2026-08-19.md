# Как курсы попадают на платформу — один контракт, три писателя

Дата: 2026-08-19
Статус: **решение принято; шаги 1–3 реализованы 2026-08-19** (гейт готовности, сервис записи, CLI импорта и экспорта). H2/H3 — впереди.
Связано: `docs/lms-research-2026-08-15.md` (§4, §6), `docs/lms-h1-implementation-2026-08-15.md` (развилка «git vs БД»).

## Проблема

Курс на платформу сейчас попадает ровно одним путём: я редактирую `data/courses/*.json` в репо, гоняю `lms:validate`, потом `lms:seed` зеркалит структуру в Postgres. Это работает для своих курсов и не работает ни для чего другого:

- внешний автор не будет открывать git;
- билдера в кабинете нет, а когда он появится — он будет писать в БД, то есть возникнет второй источник истины;
- агент (мой в Claude Code, авторский в кабинете) сегодня пишет **файл**, а завтра должен писать **строку в БД** — и это разные пути записи с разными гарантиями.

Развилку «git или БД» H1-док оставил открытой по срокам. Здесь она закрывается.

## Решение

**Одна точка записи для всех трёх писателей. Источник истины — БД. Git — экспорт, а не вход.**

```
              ┌──────────────────────────────────────────┐
я в Claude Code ─┐                                        │
                 │                                        │
билдер в кабинете ├──► authoring service ──► validate ──► readiness ──► lms_* (Postgres)
                 │    (один код, три вызывающих)                              │
агент автора ────┘                                                            │
                                                                              ▼
                                                          npm run lms:pull → data/courses/*.json (git = ревью/бэкап)
```

Три следствия, каждое из которых уже частично лежит в коде:

1. **Контракт один и он уже есть** — `Course → Module → Lesson → Block[]` из `src/lms-core`. Ни билдер, ни агент не получают «сырого» доступа к БД: любая мутация проходит `validateCourse` и те же коды ошибок `lms_*:path`, что и сид.
2. **Валидация ≠ готовность к публикации.** `validateCourse` отвечает «структура цела». Публикация требует второго гейта — `courseReadiness()`: нет ли `[ЗАПОВНИ]`-маркеров, есть ли `boundary_note` в телесном протоколе, у всех ли `video` реальные id, непрерывна ли последовательность дней. Этот гейт — то, что превращает агентную генерацию из риска в рабочий процесс: агент имеет право оставить дырку, но не имеет права опубликовать курс с дыркой.
3. **Git остаётся, но разворачивается.** `lms:seed` (файл → БД) доживает до переключения; после него работает `lms:pull` (БД → файл): курс в git как снимок опубликованной версии, для ревью через diff, истории и отката.

## Почему не наоборот (БД → экспорт, а не git-as-CMS навсегда)

Git-as-CMS хорош ровно до первого автора, который не программист. Дальше он даёт две модели источника одновременно — «наши курсы в файлах, чужие в базе» — то есть два пути записи, два способа отката и вопрос «где правда» на каждом курсе. Этот промежуточный вариант отвергнут ещё 2026-08-15; здесь он отвергается повторно и с датой переключения.

## Когда переключаем

Триггер — **первый курс, который заводит не я**. До этого момента:

- пишем `authoring service` и `courseReadiness` (они нужны в любом случае — их зовёт и сид, и билдер, и агент);
- продолжаем вести свои курсы файлами: `data/courses/*.json` → `lms:seed`.

В момент переключения: `lms:pull` становится обязательным шагом релиза, `catalog.ts` меняет тело (читает БД, кеширует), вызывающие не меняются — он и был задуман как единственная точка чтения.

## Что реально делает каждый из трёх писателей

| Писатель | Вход | Через что пишет | Чем ограничен |
| --- | --- | --- | --- |
| **Я в агентной среде** | авторские docx/pdf/видео + разговор | `npm run lms:import <file>` → authoring service | тот же `courseReadiness`; статус `draft`, пока есть `[ЗАПОВНИ]` |
| **Билдер в кабинете** | inline-редактирование на странице курса | server action → authoring service | RLS по `author_id`; публикация только через readiness-гейт |
| **Агент автора** | чат «сделай из этого документа 14-дневный курс» | tool-calls (`course.upsert`, `lesson.upsert`, `block.generate`) = функции ядра | те же инструменты, что у билдера; не может публиковать сам |

Ключевое: **это не три пайплайна, а три UI поверх одного сервиса**. Агент — это пользователь с узким набором инструментов, а не отдельный привилегированный путь.

## Приёмка сырья (то, на чём спотыкается любой внешний автор)

Автор приносит не курс, а материалы: docx с инструкциями, pdf-протокол, видео, таблицу отчётности. Между «материалы» и «курс» нужен слой:

- `lms_course_sources` — загруженные файлы, привязанные к курсу (файл + извлечённый текст + кто загрузил);
- агент читает источники и собирает **черновик структуры**, а не готовый курс: модули, уроки, дни, объективы, чек-листы;
- всё, чего в источниках нет, помечается `[ЗАПОВНИ: что именно нужно]` и **не выдумывается** — особенно в теме здоровья. Это конвенция, а не пожелание: `courseReadiness` считает такие маркеры блокерами публикации;
- автор правит в билдере и публикует.

Именно так собран `way21` (2026-08-19): 16 уроков, авторские методические тексты перенесены из источников дословно, недостающие недельные инструкции и видео — маркерами.

## Мульти-авторность

- `lms_courses.brand` уже есть; добавляется `author_id` + роль `author` на `platform_users`.
- RLS: автор видит и правит только свои курсы; ученик читает только `published`.
- Изоляция авторов на платформе повторяет модель лендинг-сети: разные авторы — разные бренды, а не один мультибренд.

## Что сделано 2026-08-19 (шаги 1–3)

- **`courseReadiness()`** — `src/lms-core/readiness.ts`. Отвечает на вопрос «можно ли это показывать ученику», отдельно от `validateCourse` («цела ли структура»). Блокеры: маркер `[ЗАПОВНИ`, невалидный `videoId`, CTA с нерезолвящимся href, картинка без пути, отсутствие `boundary_note` в телесном протоколе. Коды `lms_ready_*:path` — как везде в ядре.
- **Гейт публикации** — в двух местах: тест `catalog.test.ts` («ни один `published` курс не имеет блокеров») и `writeCourseStructure`, который просто отказывается писать `published` с дырками. Черновик с дырками писать можно — это и есть смысл черновика.
- **`src/lib/lms/authoring.ts`** — единственная точка записи структуры: `writeCourseStructure` (валидация → гейт → upsert по id) и `courseFromRows` (обратное отображение для экспорта). Билдер и агент садятся сюда же, а не мимо.
- **CLI**: `npm run lms:seed` (переведён на сервис, больше не дублирует маппинг), `npm run lms:import -- <file.json>` (загрузка одного файла откуда угодно + git-снимок в `data/courses/`), `npm run lms:pull -- <slug>` (БД → файл, экспортная половина).
- **`scripts/lib/ts-hooks.mjs`** — 20 строк, которые позволяют `.mjs`-скриптам импортировать TS напрямую (Node сам снимает типы; хук добавляет только безрасширенные относительные импорты и алиас `@/`). Без этого «единственная точка записи» была бы недостижима из CLI и маппинг пришлось бы держать в двух экземплярах — ровно то, чем `lms-seed.mjs` был до сих пор.

Практический эффект: `npm run lms:seed:dry` теперь печатает не только «сколько уроков», а список того, что автор ещё должен — по каждому курсу. На момент внедрения: `reset-day` — 5 блокеров, `way21` — 37.
