### Приложение

- `src/lib/lms/catalog.ts` — загрузка и валидация авторского JSON при старте модуля (конвенция `generator/content.ts`).
- `src/lib/lms/server.ts` — единственное место, которое ходит в БД за учебными данными: entitlement → авто-enrollment → чтение/запись прогресса.
- `src/lib/lms/notify.ts` — **диспетчер каналов**: уведомление адресуется ученику, канал берётся с профиля. Зарегистрирован один отправитель (telegram); `email`/`webpush` объявлены и честно возвращают «нет отправителя».
- `src/lib/lms/reminders.ts` — почасовой проход по enrollment'ам с идемпотентным журналом.
- `src/components/lms/*` — рендерер блоков, карта курса, плеер урока, шторка оглавления, состояния ошибок.
- `src/components/platform/cabinet/*` — кабинет пользователя (см. «Обновление 2026-08-17» выше); читает и профиль (`/api/platform/users/me/profile`), и полку курсов (`/api/lms/me/courses`).
- Маршруты: `/learn/[course]`, `/learn/[course]/[lesson]` (оба `noindex`), `/profile` (кабинет).

## Чего проверить нельзя без твоих действий

Сквозной путь ученика (enrollment из покупки → drip → чек-лист → завершение → напоминание) **не проверялся вживую**: он требует применённой миграции и реальной оплаченной записи. Логика этого пути покрыта юнит-тестами, но это не то же самое, что прогон на данных.

## Модель контента: git-as-CMS (H1)

Контент курса — файлы в `data/courses/*.json` под git. Это content-as-code: ревью через diff, история через git log, откат через revert, ветка = черновик курса, гейт `lms:validate` = защита от битой структуры. БД хранит **зеркало** структуры (ради FK от прогресса) и все пользовательские данные — прогресс, enrollment, напоминания.

**Решение по развилке (2026-08-15):** git остаётся источником истины на первую волну — наши собственные курсы. Затем платформа **полностью переходит на БД как источник, с экспортом в git**. Промежуточный двухуровневый вариант (наши курсы в git, авторские в БД) отвергнут: две модели источника одновременно — это два пути записи, два способа отката и постоянный вопрос «где правда» на каждом курсе.

Что из этого следует для кода уже сейчас:

- `src/lib/lms/catalog.ts` — единственная точка чтения контента. Переход на БД меняет её тело, а не вызывающих.
- Формат JSON = формат БД-строк (`scripts/lms-seed.mjs` уже отображает одно в другое без потерь), поэтому будущий экспорт БД → git пишется как обратное отображение того же кода.
- `course.version` уже существует, и на нём будет строиться экспорт: снимок публикуемой версии в файл.

## Решения от 2026-08-15 (после первого прохода)

- **Старт курса — по факту входа на платформу, а не по дате оплаты.** `started_at` берётся из момента первого обращения к курсу (`ensureEnrollment`), не из `entitlement.grantedAt`. Купивший в пятницу и открывший в воскресенье начинает с дня 1: трёхдневный протокол не должен сгорать на две трети из-за даты счёта. Дата покупки остаётся в `orders` для отчётности.
- **Часовой пояс определяется автоматически.** `Intl.DateTimeFormat().resolvedOptions().timeZone` уходит в `POST /api/platform/users/me/settings` один раз за сессию (ключ в `sessionStorage`), **до** первого чтения курса — иначе день N успел бы посчитаться по старому поясу. Зона валидируется на сервере (`isValidTimeZone`), при отказе остаётся дефолт `Europe/Kyiv`.

## Открытые технические вопросы

- **`lms_progress_events` растёт без границы.** Для 21-дневного курса это десятки строк на ученика — не проблема на годы вперёд. Свёртка на чтении вместо проекции выбрана осознанно (один источник истины); если объём станет заметным, добавляется материализованная проекция, а не смена модели.
- **Смена пояса в поездке сдвигает границу дня.** Перелёт Киев → Ванкувер может «вернуть» ученика во вчера на несколько часов. Прогресс монотонен, поэтому пройденное не откатывается; сдвигается только момент открытия следующего дня. Приемлемо, но если это начнёт мешать — фиксировать пояс на enrollment вместо профиля.
- **way21 не заведён.** Структура (21 день, 3 фазы) ложится в ту же схему без изменений; нужен контент.
