## Q1. Где живёт review, когда единица продажи — контейнер

**Сегодня.** `review_status` — колонка на `lms_courses` (`20260823000000_lms_course_review.sql`), CHECK на
четыре значения `draft | in_review | changes_requested | approved`, плюс параллельная пара
`pending_content` / `pending_review_status` для правки уже живого курса
([builder.ts:141-163](src/lib/lms/builder.ts:141), [:484-549](src/lib/lms/builder.ts:484)). Продаваемость
читается из этого одной функцией:

```
saleBlockersOf({ status, reviewStatus, visibility, offer })   // src/lib/admin/catalog.ts:50-72
  status !== "published"      → not_published
  reviewStatus !== "approved" → not_approved
  visibility === "hidden"     → hidden
  offer отсутствует/withdrawn/без срока → no_offer | offer_withdrawn | no_access_rule
```

**Что ломается.** У Experience из четырёх activity разных kind нет одной строки, несущей «одобрено».
`saleBlockersOf` получает N статусов и должна свернуть их в один ответ — а свёртка ⇒ это и есть решение,
которое сейчас никем не принято. Хуже: три из пяти kind (`live`, `resource`, `human_session`) вообще не
имеют содержимого, которое можно ревьюить, поэтому «AND по всем activity» для них означает либо вечное
`not_approved`, либо молчаливое исключение.

**Варианты.**

| | Где статус | Свёртка | Цена |
| --- | --- | --- | --- |
| **A. Контейнер ревьюится, activity — нет** | `experiences.review_status`, `lms_courses.review_status` остаётся как есть и читается только билдером | Продаваемость смотрит **только** на контейнер | 1 колонка; но одобренный контейнер может содержать неодобренный курс |
| **B. Только activity, контейнер производный** | статусы остаются на исполнителях | `approved` = все ревьюибельные activity одобрены; нере­вьюибельные kind не участвуют | 0 колонок; «одобрено» перестаёт быть фактом и становится вычислением, у него нет ни времени, ни автора |
| **C. Оба, с явным правилом** | обе строки | контейнер обязан быть `approved` **и** каждая ревьюибельная activity — тоже | 1 колонка + одно правило в `saleBlockersOf` |

**Рекомендация — C.** Причина не в полноте, а в том, что `approved_at`/`approved_by` уже существуют как
*аудит* (кто и когда впустил это к людям), и вариант B их уничтожает: у вычисляемого статуса нет подписи.
При этом B прав в главном — курс, не прошедший ревью, не должен продаваться внутри одобренного пакета, и C
это сохраняет. Ревьюибельность делается свойством kind (`course`, `assessment` — да; `live`, `resource`,
`human_session` — нет), одной таблицей констант рядом с enum, не колонкой.

## Q2. Boundary-note на уровне композиции

**Сегодня.** Самый ценный инвариант кодовой базы живёт в
[readiness.ts:196-200](src/lms-core/readiness.ts:196):

```ts
if ((bodyFacing || course.schedule.mode === "daily") && !hasBoundary) add("lms_ready_missing_boundary", …)
```

`bodyFacing` поднимается из блоков `protocol_step` / `practice_block`, `hasBoundary` — из блока
`boundary_note`. То есть инвариант **блочный**, и `courseReadiness(course)` — единственный, кто его знает.

**Что ломается.** Experience «травы + консультация» телесна насквозь и не содержит ни одного блока: у
`kind='resource'` и `kind='human_session'` блоков нет вообще. Инвариант не нарушается — он **молча
выключается**. Это худший из возможных отказов: гейт, который в новой композиции просто перестаёт
существовать, при этом продолжая зелено гореть на курсах.

**Варианты.**

- **A. `experiences.contraindications` (InlineText, nullable) + правило «телесная Experience обязана его
  иметь».** Телесность объявляется на контейнере (`body_facing boolean` или производная от kind набора).
  Ровно тот слот, что §6.3 уже заложил в таблицу «claims_kind + contraindications».
- **B. Каждая activity сама отвечает за границу**; контейнер требует, чтобы хотя бы одна её объявила.
  Для курса ответ уже есть — существующий блок; для трав и сессии его придётся откуда-то взять.
- **C. Не переносить, документировать разрыв.** Дёшево и честно ровно до первой не-курсовой продажи.

**Рекомендация — A, со связкой к B.** `contraindications` на контейнере — источник истины; курс со своим
`boundary_note` **удовлетворяет** требование контейнера (иначе один и тот же текст придётся писать дважды и
он разойдётся). Практически: `experienceReadiness()` рядом с `courseReadiness()`, тот же формат блокеров,
новый код `lms_ready_missing_boundary_container`. Цена — 2 колонки и ~40 строк ядра. Вариант C приемлем
только если Phase 1 сознательно ограничен `kind='course'` и не продаёт ничего другого — тогда это надо
записать явной строкой, а не оставить как есть.

## Q3. Судьба `IMMEDIATE_PUBLISHED_FIELDS`

**Сегодня.** [publishedEditPolicy.ts](src/lib/lms/publishedEditPolicy.ts) — allow-list из двух полей
(`cover`, `sortOrder`), и — это важно — сравнение идёт **по всему объекту** с вычитанием списка:

```ts
const ignored = new Set(["cover", "sortOrder", "status", "version", "visibility"]);
for (const key of keys) if (!ignored.has(key) && canonical(live[key]) !== canonical(incoming[key])) return null;
```

Комментарий в файле называет это намеренным: «новое поле курса reviewable по умолчанию, пока кто-то явно не
решит иначе». Как защита от расширения контракта через UI это правильно.

**Что ломается.** Phase 1 добавит `Course` как минимум указатель на композицию (или `experience_id`). В ту
же секунду **каждый живой курс** начнёт требовать полного review-цикла, чтобы получить поле, которое автор
не менял и не видел. Отказ не в схеме, а в опыте: билдер молча перестанет сохранять правку обложки.

**Варианты.**

- **A. Расширить `ignored` тремя новыми полями в той же миграции.** Одна строка, работает, но именно так
  allow-list и вырождается: следующий агент добавит четвёртое.
- **B. Инвертировать: сравнивать не `Course`, а его *учебную* часть** — явный список полей, составляющих
  выпущенный продукт (`title`, `summary`, `tagline`, `results`, `schedule`, `modules`, `entitlementProductCodes`, …).
  Всё, чего в списке нет, — не продукт. Ровно противоположная защита: новое поле по умолчанию **не**
  reviewable, зато забытое учебное поле — тихая дыра.
- **C. Оставить сравнение по объекту, но вынести композиционные/системные поля из типа `Course`.**
  `experience_id` живёт на строке БД и в `BuilderCourse`, но не в `Course` — том, что валидируется,
  версионируется и уезжает в `pending_content`.

**Рекомендация — C, с A как страховкой.** `Course` в этом репо — снапшот учебного продукта: он целиком
кладётся в `pending_content`, в version history и в portable-экспорт. Указатель на контейнер там не место
по существу, а не только ради этой политики — контейнер владеет курсом, не наоборот. Если по какой-то
причине поле всё же обязано попасть в `Course`, тогда A, но с тестом «в `ignored` нет ничего, что учит».
B не рекомендую: он меняет направление отказа с «лишний review» на «пропущенный review», а цена этих двух
ошибок несимметрична.

## Q4. Мульти-оффер: `UNIQUE(code)` и `.maybeSingle()`

**Сегодня.** `lms_course_offers.code text NOT NULL UNIQUE`, индекс по `course_id`, но **уникальности по
`course_id` нет** — схема «один оффер на курс» держится не констрейнтом, а тем, что никто не вставил
вторую строку. На это опирается работающий код:

- [server.ts:260-273](src/lib/lms/server.ts:260) — `.eq("course_id", …).maybeSingle()`. При двух строках
  `.maybeSingle()` возвращает **ошибку**, `data` = null, и `readAccessRule` вернёт `null` → `planAccess`
  прочитает это как **вечный доступ**. Отказ тихий и в сторону раздачи.
- Комментарий там же прямым текстом обосновывает отказ от фильтра `active` фразой «`code` уникален на курс,
  поэтому строка ровно одна, а не история». Второй оффер разрушает не только запрос, но и это рассуждение:
  у покупателя закрытого оффера и покупателя нового срок разный, а строка выбирается произвольно.
- [catalog.ts:91-93](src/lib/admin/catalog.ts:91) — `new Map(offerRows.map(row => [course_id, …]))`: при
  двух строках побеждает последняя, и админка показывает не ту цену.

Комментарий самой миграции при этом уже предвидит пакет с сопровождением рядом с курсом.

**Варианты.**

- **A. Оставить один оффер на Experience и закрепить это констрейнтом** (`UNIQUE(experience_id)`).
  Композиция и так даёт вторую форму продажи: «курс» и «курс + сопровождение» — это две Experience над
  общим курсом. Мульти-оффер оказывается не нужен.
- **B. Разрешить N офферов на Experience** (`UNIQUE(experience_id, code)`), одна помечена дефолтной.
  Тогда нужны: выбор оффера в чекауте, «какой срок у этого покупателя» из `orders`, а не из курса, и
  переписывание трёх мест выше.
- **C. Отложить, но убрать мину:** сегодня же добавить `UNIQUE(course_id)`, чтобы схема утверждала то, во
  что код верит.

**Рекомендация — A, и C немедленно, не дожидаясь ответа.** A согласуется с §6.1: ширина форм приходит
композицией, а не новыми типами — и это же правило снимает главный аргумент за B. Срок доступа и цена
описывают *то, что человек проходит*; две цены за одно и то же — это две разные вещи, которые он проходит.
C стоит одну строку DDL и снимает единственный тихий отказ в сторону бесплатного вечного доступа. Если
ответ всё же B, то первым шагом становится перенос срока с оффера в `orders` — и это отдельная волна,
которую надо запланировать до, а не после `experiences`.

## Q5. CHECK-константы против Postgres enum

**Сегодня.** Enum'ов в схеме нет вообще: `status`, `review_status`, `visibility`, `locale` — везде
`text` + `CHECK (… IN (…))`, снимаемый и пересоздаваемый в миграции (`DROP CONSTRAINT IF EXISTS` →
`ADD CONSTRAINT`). Идиома выдержана на 17 миграциях.

**Что решается.** `experience_activities.kind` — первый кандидат в `CREATE TYPE`, и §4 п.5 просит
выбрать сознательно, а не по инерции.

**Варианты.** `CREATE TYPE`: значения видны в интроспекции, опечатка невозможна, генератор типов
Supabase выдаёт union автоматически. Против: `ALTER TYPE … ADD VALUE` не откатывается и до недавнего
времени не выполнялся в транзакции — а `kind` — это ровно тот столбец, куда §6.3 велит класть слоты
(`live`, `resource`) заранее, то есть добавлять значения будут часто. CHECK: расширяется обычным
DDL, удаление значения — тоже DDL, всё транзакционно; цена — список значений дублируется в TS.

**Рекомендация — CHECK, то есть сохранить идиому.** Не из консерватизма: правило «слот = enum-значение
без реализации» означает, что этот столбец по замыслу растёт, а `ALTER TYPE` — самая неудобная в откате
операция из всех, что репо себе позволяет. Плюс единообразие: один способ читать схему стоит дороже, чем
интроспекция одного столбца. Дублирование в TS закрывается тем же тестом-гардом, каким закрыты локали.
