# Доступ до програм: покупка, вікно, ворота

2026-08-26. Контракт: `src/lms-core/access.ts` → `src/lib/lms/server.ts` →
`src/lib/admin/access.ts`. Міграція: `docs/migration/sql/2026-08-26_program_access_windows.sql`.

## Принцип

Оплата і доступ — різні речі, і вони лишаються різними.

- **Оплата** відповідає на «чи була покупка». Це `orders` + WayForPay-вебхук.
  Нічого в цьому шарі не змінено.
- **Доступ** відповідає на «до якої програми, з якої дати, до якої дати». Це
  один рядок `lms_enrollments` на пару (курс, акаунт).

Покупка — підстава для доступу, а не сам доступ. Тому доступ можна видати без
оплати (подарунок, промо), закрити при живій оплаті (повернення коштів) і
продовжити без нової покупки.

## Два годинники, і вони різні

| | що це | від чого рахується |
|---|---|---|
| `started_at` | день 1 крапельниці уроків | **перше відкриття** курсу |
| `expires_at` | кінець купленого | **дата оплати** + термін оферу |

Купив у п'ятницю, відкрив у неділю — протокол на три дні починається в неділю,
але 30 днів доступу рахуються з п'ятниці. Це те, за що заплатили, і те, що
показує чек.

## Термін живе в офері

`lms_course_offers.access_days` / `access_lifetime` — поруч із ціною, під
admin-only політикою. Термін продають, як і ціну; автор у білдері його не
змінює. CHECK у базі не дає створити офер без явного правила, а
`npm run admin:offer` відмовиться зробити новий офер без `--access-days=N` або
`--access-lifetime`.

`lms_courses.access_note` — окреме поле і лишається прозою для сторінки офера.
Вони свідомо можуть розходитись: у тексті «доступ на місяць», а конкретному
учневі підтримка додала тиждень.

```bash
npm run admin:offer -- --slug=reset-day --amount=795 --access-days=30
```

## Стан доступу виводиться, а не зберігається

`accessStateOf()` дає одне з чотирьох:

- `active` — відкрито;
- `expired` — `expires_at` у минулому. **Не статус у базі**: дата минула — двері
  зачинились тієї ж секунди, без будь-якого крона;
- `revoked` — операторське рішення;
- `blocked` — бан.

## Повторна купівля

`planAccess()` вирішує все одним правилом: покупка «свіжа», якщо вона пізніша за
те, до чого прив'язане поточне вікно (`order_ref`), і пізніша за відкликання.

- перша покупка → вікно від оплати;
- купив знову **після** завершення → нове вікно від нової оплати;
- купив знову **до** завершення → термін **додається** до залишку, обнулення
  немає;
- повторний захід тим самим замовленням нічого не додає — якір рухається разом
  із видачею.

## Revoke ≠ бан

| | що робить | що відкриває назад |
|---|---|---|
| `revoke` | `status='revoked'`, рядок і прогрес лишаються | реактивація адміном **або нова оплата** |
| `block` | `blocked_at` | тільки зняття блокування руками |

Відкликання закриває місце, куплене **тією** оплатою; нова оплата — це нова
угода. Бан — про людину, і в нього не має бути ціни.

Раніше revoke видаляв рядок. Це губило прогрес і скасовувало саме себе:
entitlement виводиться з оплачених `orders`, які лишались, тож наступний захід
створював рядок наново.

## Ворота

Один вхід: `ensureEnrollment()` → `loadLearnerCourse()`. Через нього проходять
сторінка курсу, сторінка уроку і кожен запис прогресу, тому пряме посилання не
щасливіше за кабінет. Відмови: 403 `not_entitled | expired | revoked | blocked`,
404 `not_published`, 423 для ще не відкритого уроку.

Кабінет нічого не ховає: непридбана програма видима з кнопкою «Придбати
доступ», прострочена — з «Продовжити доступ», активна — з датою завершення і
залишком днів.

## Джерела доступу

`order` | `token` — покупка; `manual` — видача адміном; `bonus`, `promotion` —
щоб через рік було видно, чому в людини є доступ. Ручна видача пише
`granted_by`.
