# Витрина + LMS + билдер — ресерч решений

Дата: 2026-08-22
Статус: research → proposal (реализационные решения фиксируются здесь; долговечные правила промоутятся в ReOS `Архитектура.md` по `docs/CANON.md`)
Продолжает: `docs/lms-research-2026-08-15.md` (карта рынка LMS — не дублируется здесь), `docs/lms-builder-2026-08-21.md` (что построено), `docs/platform-scale-plan.md` (фазы)

Прошлый ресерч отвечал на вопрос «какую LMS строить» и был написан **до** того, как билдер появился. Этот отвечает на другой: три поверхности уже существуют, и вопрос в том, **чем они друг другу являются**. Рынок LMS здесь не пересматривается — пересматривается стык.

## 0. Три поверхности — это одна цепочка, а не три продукта

```
БИЛДЕР            ВИТРИНА                       LMS
автор пишет  →    покупатель находит и платит →  ученик проходит
build.*           /programs, /products, оффер    /learn/*
```

Каждое звено имеет свой источник истины. Именно расхождение источников — главный результат этого аудита.

## 1. Фактическое состояние: где чей источник истины

| Звено цепочки | Что это в коде | Источник истины | Кто может изменить |
| --- | --- | --- | --- |
| Структура и контент курса | `lms_courses/modules/lessons` + `data/courses/*.json` как снимок | **база** (`src/lib/lms/liveCatalog.ts`) | автор в билдере, живьём |
| Карточка в каталоге | `programs` в `src/lib/platform/content.ts` (452 строки) | **код** | только разработчик + деплой |
| Страница оффера | отдельный `page.tsx` на программу (`/programs/way21`, `/programs/reset-day`, …) | **код** | только разработчик + деплой |
| Цена и способ оплаты | `PRODUCTS` в `src/lib/products.ts` | **код** | только разработчик + деплой |
| Доставка после оплаты | `fulfilment: {kind: "course" \| "bot" \| "cabinet"}` там же | **код** | только разработчик + деплой |
| Право доступа | `orders` + `manualGrants` → `src/lms-core/access.ts` | **база** | оплата, `lms:grant` |
| Прохождение | `lesson_progress` (события) | **база** | ученик |

Читается за один взгляд: **две крайние трети цепочки живут в базе, середина — в коде.**

## 2. Главный разрыв: билдер публикует курс, который нельзя ни найти, ни купить

Хвиля 2 закрыла ровно половину задачи. Автор действительно правит и публикует **вживую** — `liveCatalog` отдаёт строку из базы, `revalidateTag` сбрасывает кэш в момент записи, и это проверено на проде. Но всё, что превращает курс в **товар**, осталось в TS-файлах:

Чтобы новый курс из билдера стал продаваемым, сегодня нужно, руками разработчика и с деплоем:

1. дописать запись в `programs` (`content.ts`) — заголовок, теги, артворк, `results[]`;
2. создать `src/app/(platform)/programs/<slug>/page.tsx` — динамического маршрута `[program]` не существует;
3. дописать запись в `PRODUCTS` — сумму, валюту, `fulfilment: {kind:"course", courseSlug}`;
4. задеплоить.

Следствия, которые стоит назвать прямо:

- **Полка `/learn` показывает только купленное.** Витрины курсов как таковой нет — есть витрина шести программ, зашитых в код. Курс, созданный автором, не появляется нигде: ни в каталоге, ни в поиске, ни в sitemap.
- **Единственный путь к такому курсу** — `npm run lms:grant` и прямая ссылка `/learn/<slug>`. То есть билдер сейчас — инструмент для **редактирования двух существующих курсов**, а не для запуска новых.
- **H2 объявлен «внешние авторы»**, но внешний автор не может довести свой курс до покупателя без владельца репозитория. Это ровно та зависимость, которую хвиля 2 сняла с контента и не сняла с продажи.
- **`fulfilment.kind` уже несёт правильную абстракцию** (`bot` / `course` / `cabinet`) — но живёт в захардкоженной таблице, поэтому не масштабируется.

Это не «недоделка билдера». Это архитектурный вопрос: **что является источником истины для оффера.**

## 3. Витрина — что делают те, кто решил эту задачу

### 3.1 Референсный паттерн: каждая система авторитетна для своего, связь по ссылке

Устойчивая схема в headless-commerce 2026 формулируется одинаково у Vendure, Strapi и Shopify-headless: **коммерческий бэкенд авторитетен для товара, цены и наличия; CMS авторитетна для вёрстки и редакторского текста; связь — по ID, а не копированием.** Фронт читает из CMS список ID и подтягивает живые данные о товаре из коммерческого API, поэтому цена на витрине не может разъехаться с ценой на кассе. Инвалидация — вебхук из CMS в revalidate-эндпоинт фронта.

Для нас это переводится буквально:

- **база LMS авторитетна** для того, что курс вообще есть, как называется, чей он, опубликован ли, какая у него обложка и тема;
- **код остаётся авторитетным** для маркетингового текста конкретных флагманов (way21, reset-day) — это не «контент курса», это лендинг, и его качество — актив;
- склеиваются они **по slug**, а не дублированием заголовков.

Практический вывод: не «переносим витрину в базу целиком», а **добавляем второй, дешёвый класс оффера**. Флагманы остаются авторскими страницами; новый курс автора получает сгенерированную страницу по данным из базы. Один динамический маршрут `/programs/[slug]`, который отдаёт 404, если для slug есть рукописная страница.

### 3.2 Моделирование цены: Stripe против Medusa

Два зрелых полюса, и они дают вилку для нашего решения:

- **Stripe**: `Product` (что продаём) отдельно от `Price` (сколько и как часто). Одна сущность может нести несколько цен — разовую и подписочную. Просто, и этого хватает большинству.
- **Medusa**: между товаром и ценой вставлен слой — `PriceSet` (набор цен в разных валютах) и `PriceList` (группа цен, включающаяся при выполнении условий: даты начала/окончания, сегмент покупателя). Акции и «VIP-цена» становятся данными, а не кодом.

Наш `PRODUCTS` сейчас — это даже не Stripe-модель: цена, валюта, доставка и Meta-нейминг слиты в одну запись на продукт. Что уже больно:

- **тестовая цена в 1 UAH** живёт как константа `TEST_PRICE_UAH` внутри файла, с инструкцией «grep CW_TEST_PRICE_1UAH, чтобы откатить». В модели Medusa это был бы `PriceList` с датами, который истекает сам;
- **«апгрейд-залік» reset-day → way21** (Phase 0 в `platform-scale-plan.md`, названный load-bearing KPI) требует условной цены по сегменту — это ровно `PriceList` с правилом «владеет reset-day»;
- **валютная витрина для EN-аудитории** (§3A прошлого ресерча) — это `PriceSet` с несколькими валютами.

Рекомендация — **не Medusa, а её форма**: разделить `PRODUCTS` на `product` (что, доставка, нейминг) и `prices[]` (сумма, валюта, окно дат, условие). Это ~день работы, ноль новых зависимостей, и оно снимает три отложенных вопроса разом.

### 3.3 Чего на витрине нет и чего рынок ожидает

Из аудита: нет поиска, нет фильтров, нет сортировки, нет страницы «все курсы» (в отличие от «все программы»), нет структурированной разметки `Course`/`Product` для поисковиков на сгенерированных страницах, нет превью-урока для незалогиненного. Последнее — прямое требование Phase 0 («free sample day»), до сих пор не закрытое, и в модели данных для него всё уже есть: `lms_lessons` + флаг `preview`.

## 4. Билдер — что делают зрелые редакторы структурированного контента

Ближайший референс не «конструкторы курсов» (это лендинг-билдеры, у нас другая задача), а **Payload CMS** — потому что у него та же форма: типизированная схема, черновики, публикация, Next.js на другом конце.

Что у Payload есть и чего у нас нет:

| Механика Payload | Как устроена | Что закрывает у нас |
| --- | --- | --- |
| **Versions** | каждая запись хранит историю версий отдельной таблицей | у нас `lms_courses.version` — это счётчик, а не история: правка урока необратима, отката нет, а git перестал быть историей контента в тот момент, когда источником стала база |
| **Drafts** | поле `_status`, черновик поверх опубликованного | у нас `status` на **курсе**, но не на уроке: правка опубликованного урока видна ученику сразу, промежуточных состояний нет |
| **Autosave** | автосохранение в новую draft-версию по интервалу | у нас «незбережене і навігація» решено предупреждением — то есть проблема названа, но не снята |
| **Scheduled publish** | `schedulePublish: true`, дата в будущем | когорты и сезонные циклы (Phase 3) сейчас требуют присутствия человека в нужный час |
| **Server-side Live Preview** | админка держит витрину в `<iframe>`, на сохранение шлёт `postMessage`, страница делает `router.refresh()` | у нас превью есть, но это отдельный режим билдера, а не настоящая страница ученика — то есть «что увидит ученик» проверяется приблизительно |

**Sanity** добавляет ещё одну идею, важную именно для нас: **Content Releases** — пачка изменений, которая публикуется атомарно. Для курса из 21 урока это разница между «автор правит живой курс на глазах у людей, которые в нём находятся» и «автор готовит версию 2 и выкатывает её одним движением». С учётом того, что `liveCatalog` теперь отдаёт базу мгновенно, отсутствие такой пачки — риск, который мы сами себе создали хвилей 2.

Порядок по цене/пользе: **версии уроков → автосохранение → релиз-пачка → отложенная публикация**. Живое превью в iframe — дорого и не первоочередно, наш `data-cw-pack` уже даёт визуально верную картинку.

## 5. LMS-плеер — что говорят данные о завершаемости

Цифры 2026 года устойчиво повторяются в разных сводках:

- маркетплейсы (Udemy-класс) — **ниже 15%** завершения;
- self-paced на собственной платформе — **30–50%**;
- когортные программы с живыми встречами — **50–80%**, отдельные случаи выше;
- курсы с обсуждением внутри — **65% против 43%** без него.

Вывод, который делают сами обзоры, стоит процитировать по смыслу: типовой ответ на низкую завершаемость — короче видео, больше квизов, геймификация, дрип, письма-напоминания — **не ошибочен, но недостаточен: это лечение социальной проблемы контентными средствами.**

Что это значит для нас конкретно:

1. **Мы уже в верхней половине по форме**: протокол на 21 день с дневным ритмом и напоминаниями — это ближе к когорте, чем к self-paced. `CourseSchedule` с `mode: daily` и `gate: soft` — правильное решение, и «soft по умолчанию» отдельно правильное (человек, купивший протокол, должен видеть третью неделю в первый день, чтобы понимать, что заказывать).
2. **Социального слоя нет вообще** — ни обсуждения, ни когортного старта, ни видимости других участников. Это самый большой одиночный рычаг завершаемости по данным, и он же самый дорогой в поддержке для соло-автора (потолок мощности — риск №5 в `platform-scale-plan.md`). Компромисс, который просматривается: **когортный старт без чата** — `start: "date"` уже есть в схеме, а «вы идёте вместе с 40 людьми, сегодня день 4» не требует модерации.
3. **Квизов нет** — `quiz_block` перечислен в модели прошлого ресерча, но среди 12 реализованных типов блока его нет. Как инструмент завершаемости он слабый; как инструмент **сегментации** (дошa-логика уже есть) — сильный.
4. **Сертификата нет.** Для медицински-смежной темы с «ограниченными заявлениями о здоровье» это скорее осознанное благо, чем пробел. Отмечаю, чтобы не всплывало как «забыли».

## 6. H3 — агент: что изменилось в стандартах за год

`docs/agent-contour-2026-08-21.md` принят, но не построен. Индустрия за это время сошлась на трёх вещах, и все три у нас уже наполовину есть:

- **Структурированный контент как контекст агента.** Типизированные, запрашиваемые модели, по которым агент может рассуждать — против свободного HTML. Наш `lms-core` с ручными валидаторами и кодами `lms_*:path` — ровно это, и ноль зависимостей делает его пригодным для передачи агенту как схемы.
- **MCP как поверхность инструментов.** Sanity отдаёт 40+ инструментов через MCP-сервер: операции над документами, схема, релизы. У нас маршруты `/api/lms/authoring/*` уже играют эту роль — им не хватает описания как инструментов.
- **Guardrails и аудит.** Общий вывод обзоров: генеративное авторство без валидации схемы, ревью и журнала изменений создаёт риск публикации на скорости машины. У нас валидация схемы есть (агент не может опубликовать то, что отверг бы сид — это уже инвариант билдера), **журнала изменений нет**. Это второй аргумент за версии уроков из §4: они нужны не для удобства автора, а как условие безопасного допуска агента к записи.

Порядок правильный: **версии → потом агент**, а не наоборот.

## 7. Рекомендации, по стоимости и рычагу

**P0 — снять разрыв «билдер публикует то, что нельзя купить».** Без этого H2 не выполнен по своему же определению.
- `lms_courses` получает поля витрины: `summary`, `tagline`, `results[]`, `visibility: hidden|unlisted|listed`;
- динамический `/programs/[slug]` для курсов без рукописной страницы; рукописные шесть выигрывают по приоритету;
- `product`/`prices[]` вместо слитого `PRODUCTS`, с `fulfilment.kind:"course"` по `courseSlug` из базы;
- `/learn` и `/programs` начинают показывать курсы из базы, а не только шесть констант.

**P0 — состояние на 2026-08-22.** Первый шаг сделан: `docs/migration/sql/2026-08-22_lms_course_storefront.sql` добавляет `lms_courses.tagline / results / visibility` и отдельную таблицу `lms_course_offers`. Модель, маппинг и авторские поля в билдере на месте.

Решение владельца, зафиксированное здесь: **цену назначает только владелец.** Отсюда две таблицы, а не одна. Автор владеет тем, чем курс *является* — название, описание, слоган, обещания, и достаточно ли он готов, чтобы стоять в каталоге; всё это контент и живёт рядом с контентом. Владелец владеет тем, сколько курс *стоит*: цена — не утверждение о материале, а обязательство бизнеса перед покупателем, и внешний автор, который мог бы её назначить, назначил бы себе выплату. Разные таблицы — разный грант, и маршруты авторинга на `lms_course_offers` гранта не имеют. Слить их в одну строку значило бы сделать «кто может писать эту колонку» деталью политики вместо структурного факта.

`visibility` — это **не** `status`. `status` говорит, открыт ли материал тем, кто уже купил; `visibility` — могут ли чужие его найти. Они независимы: курс, который продают только через лендинг, опубликован и unlisted; готовый курс, ждущий цены, опубликован и hidden. По умолчанию `hidden` — миграция не имеет права выставить что-либо на продажу.

Осталось по P0: динамический `/programs/[slug]`, каталог из базы, и платёжный путь `course:<slug>` через `lms_course_offers`.

**P1 — версии уроков + журнал изменений.** Условие безопасности для живой публикации, которая уже включена, и предусловие для агента.

**P2 — превью-урок для незалогиненного.** Phase 0 требует «free sample day» с 2026-07; данные для этого есть, нужен флаг `preview` на уроке и публичный маршрут.

**P2 — когортный старт без чата.** Дешёвая часть 5-кратного эффекта когорт, без нагрузки на автора.

**P3 — релиз-пачка (Content Releases) и отложенная публикация.** Становится обязательной, когда авторов станет больше одного.

**Не делать сейчас:** живое iframe-превью (дорого, выигрыш мал при `data-cw-pack`); чат/сообщество (упирается в потолок соло-автора — сначала когортный старт и измерить); сертификаты; коллаборативное редактирование (Yjs) — у курса один автор, как и записано в прошлом ресерче.

## 8. Открытые вопросы

1. **Может ли внешний автор назначать цену сам?** Технически P0 это позволяет; коммерчески это решение владельца (модель Kwiga: $15/мес плюс за число студентов — вопрос H2+, до сих пор открытый).
2. **Рукописная страница оффера против сгенерированной — где граница?** Предложение: флагманы, за которые покупается трафик, остаются рукописными; всё остальное генерируется. Порог не определён.
3. **`data/courses/*.json` — зачем они теперь?** Как fallback-снимок оправданы. Как «источник» — уже нет, и они уже разошлись с базой (`file=2 db=3` для reset-day, `file=4 db=5` для way21). Нужно решить, снимок ли это, обновляемый автоматически при публикации, или артефакт, который со временем убирается.
4. **Тестовая цена 1 UAH** всё ещё в `PRODUCTS`. Это не ресерч-вопрос, а незакрытый хвост QA, и он опасен ровно с момента прихода трафика.
